# 性能目標とフリーズ防止設計
状態：未測定の**開発目標**。達成を保証するものではない。

## なぜ性能を最優先にするか
旧v4の独立WebViewベースでは、起動直後や画像切り替え時に「応答なし」になる実機症状が続いた。v5はQtネイティブUIと処理分離を前提に設計し、同様の失敗を回帰試験で捕捉する。

## 初期指標
| メトリクス | 目標・観測条件 |
| --- | --- |
| 起動→空画面表示 | 3秒以内を目標（対象PC別に実測） |
| クリック→視覚反応 | 100ms以内を目標。高負荷中も操作継続 |
| PDF 40ページ | メタデータ読み込みと最初のプレビューを先行 |
| 画像キャッシュ | 初期上限64MiB（処理内部やOSの総メモリ上限ではない） |
| ズーム | 50〜300%、不要な全面描画を抑制 |
| 切り出し | 選択ROIだけ描画。全40ページの巨大画像を保有しない |
| プロセス | 初期ワーカー1。並列増加は効果測定後 |

## 必須の実装規則
- PyMuPDF呼び出しをGUIメインスレッドに置かない。
- PyMuPDFオブジェクトを複数スレッドで共有しない。
- 1回のUI操作で全ページのサムネイルを再構築しない。
- 「最後の要求が勝つ」方式で古いズーム要求の結果を破棄する。
- 高DPIディスプレイでは実ピクセル数を基準にコストを計算。
- 画像生成は「現在ページ」優先とし、一覧の先読みは負荷時に止める。
- 保存・OCRを含む長い処理は開始/終了/キャンセル状態を表示する。
- 起動時の外部ネットワーク・Webフォントは不要とする。

## 評価シナリオ
1. 空画面で連続30クリック、ウィンドウ移動・閉じる、各UIモード切替。
2. 40ページ人工スキャンPDFで、次/前を連続操作しながら300%へズーム。
3. 40ページのROI抽出一覧を開き、速いスクロール・画像拡大・再縮小。
4. 途中で切り出し範囲を変え、古い描画結果が上書きしないか確認。
5. 保存中にウィンドウが「応答なし」にならないか確認。
6. 低メモリ/高DPI/別Windows端末/オフラインで再試験。

## ログと診断
開発ビルドで起動時間、UI操作レイテンシ、描画要求数、画像キャッシュサイズ、ワーカー失敗、メモリ使用量を記録。個人のPDFパスや内容を外部送信しない。診断ログに敏感情報を残さない。

## alphaの実装済み対策と未確認事項
実装済み：描画の別プロセス化、可視領域クリップ描画、6MPの画素上限、ズーム時の要求遅延、サムネイル遅延取得、要求世代番号による古い応答の除外。いずれも実機のフリーズを解消したことは未確認。
